# 00. はじめに — なぜ移行するのか

## そもそも dotfiles とは

`.bashrc` や `.gitconfig` のように、ドット (`.`) から始まる設定ファイルの総称。ホームディレクトリに置かれ、シェルやエディタの挙動を決める。

これを Git リポジトリで管理し、新しいマシンでも同じ環境を再現できるようにする、というのが「dotfiles リポジトリ」の目的。

## 今どうなっているか

`./main.bash setup` を実行すると、次の 3 つが起きる。

1. `~/.bashrc` と `~/.zshrc` に「リポジトリ側のファイルを読み込む行」を**追記**する
2. 設定ファイルを `~/.config/...` などへ **symlink** する
3. bash-completion を `curl` でダウンロードする

<details><summary>symlink (シンボリックリンク) とは</summary>

「別のファイルを指す小さな目印」。`~/.tmux.conf` を `~/dotfiles/tmux/home.tmux.conf` への symlink にしておくと、`~/.tmux.conf` を読もうとしたプログラムは実際にはリポジトリ内のファイルを読む。

コピーと違って**実体が 1 つ**なので、リポジトリ側を編集すれば即座に反映される。この「即時反映」が今の運用の利点だった。

</details>

さらに、**シェルを起動するたびに**次のことが起きる。

- `shell/060_mise.sh` が `~/.config/mise/config.toml` を `sed -i` で書き換え、16 個のパッケージを登録する
- `shell/252_alias_mise.sh` が日に一度バージョンを固定 (pin) する
- `.fish/010_fish_fisher.fish` が fisher を `curl` で取得し、日に一度更新する

![変更前アーキテクチャ](../plantuml/out/01_before.svg)

## 何が困っているのか

### 1. 配置状態が不透明で、確実に取り消せない

何がどこに配置されたかを一覧する手段がない。「適用したら何が変わるか」を事前に見ることもできない。

さらに `Makefile` の `clean` は、13 個ある配置先のうち **4 個しか** `unlink` しない。つまり確実なアンインストール経路が存在しない。

### 2. 起動のたびに設定ファイルが書き換わる

`sed -i` によるファイル書き換えが毎回走る。複数のシェルを同時に起動すると競合するため、`flock` による排他制御まで自前で実装されている。

<details><summary>flock とは</summary>

ファイルを使った排他ロックの仕組み。「今このファイルを触っているプロセスがいるから待て」を実現する。

複数のターミナルを同時に開いたときに `sed -i` が同じファイルを壊さないよう、`shell/060_mise.sh` は `/tmp/mise_config_lock` を使ってロックを取っている。**そもそも起動のたびに書き換えなければ不要な仕組み。**

</details>

そして日次のバージョン固定処理は、**ロックファイルの役割を手で再実装したもの**にほかならない。

<details><summary>ロックファイル (lockfile) とは</summary>

`package-lock.json` や `Cargo.lock` のように、依存パッケージの**正確なバージョン**を記録したファイル。

これがあるおかげで、別のマシンでも別の日でも、まったく同じバージョンが再現される。Nix ではこれが `flake.lock` にあたる。

</details>

### 3. 暗黙の依存がある

`.gitconfig` は `pager = delta` を指定している。しかし `git-delta` はどの管理下にもなく、**手動でインストールされている前提**だった。新しいマシンでは `git diff` が動かない。

また `bat` / `eza` / `fd-find` / `procs` / `ripgrep` の 5 つは `cargo-binstall` 経由で **ソースからビルド**されている。初回セットアップに時間がかかる。

### 4. OS 差分を手で切り替えている

`.gitconfig` の 1Password 署名プログラムのパスは、WSL 用と Windows 用がコメントアウトで並んでおり、**手で切り替える**運用になっている。切り替えたまま誤ってコミットする事故が起きやすい。

## Nix で何が変わるのか

| 今 | 移行後 |
| --- | --- |
| 何が配置されるか分からない | 適用前に配置ツリー全体を読める |
| 確実に取り消せない | 世代を戻せば一瞬で元に戻る |
| 日次 pin の自作ロジック | `flake.lock` |
| ソースビルド | バイナリキャッシュからダウンロード |
| OS 差分を手で切り替え | 設定ファイル内で自動分岐 |
| `git-delta` が未管理 | 宣言に含まれる |

## 移行しても壊れないようにする工夫

いちばん大事な設計判断は、**既存の仕組みを一切壊さない**こと。

- 既存ツリー (`shell/`, `.bash/`, `.zsh/`, `.fish/`, `.config/`, `main.bash`) は変更しない
- 設定ファイルは `nix/files/` へ**複製**する
- したがって、何かあれば **`./main.bash setup` を実行すれば元の世界に戻る**

![段階移行](../plantuml/out/03_staging.svg)

移行は 6 段階に分けて進む。Stage 1 と 2 はツールを入れるだけで設定ファイルに触らないため、既存環境と**構造的に衝突しない**。
